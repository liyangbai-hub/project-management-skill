# 模式三：证据化审查规范

本文件是模式三的正式规范，适用于审查代码、配置、数据流程、技能、提示词、规则和文档。

**核心原则：宁可少报，不可虚报；先证明问题，再讨论修复。** 交付物是可复核的覆盖记录和经过验证的结论，不是篇幅庞大却无法复现的报告。

## 一、审查契约

每轮审查开始前建立契约。信息不足且影响范围、授权或判断标准时先向用户澄清，不擅自扩大任务。

| 字段 | 必须说明 |
|---|---|
| 审查目标 | 本轮要回答的具体问题，以及期望降低的风险 |
| 对象与范围 | 项目、目录、文件、模块、流程、版本、环境或场景；应可枚举或可判定 |
| 范围外内容 | 明确不检查的对象、平台、维度及原因 |
| 修改授权 | 只读，或允许修改的确切对象与操作类型；“可以处理”不等于无限授权 |
| 独立标准 | 判断正确性所依据的外部基准（见第三节） |
| 验证方式 | 静态追踪、最小复现、自动测试、手工场景、实际运行或对照实验 |
| 完成标准 | 何时可以停止、交付哪些证据、允许保留哪些未验证项 |

还应记录环境限制、敏感信息边界、不可逆操作边界和是否允许外部交互。目标或范围变化时先更新契约或取得补充授权。

**只读红线：** 用户说“只检查”“只报告”“不要动”“只读”或同等意思时，全程不得修改文件、配置、数据、历史、权限、元数据或审查对象，也不得通过格式化、自动修复、生成锁文件、更新快照等方式旁路写入。**发现致命问题同样不构成越权理由。** 应记录风险与建议动作，等待另行授权。

## 二、覆盖底账

审查前盘点对象，审查中维护底账，交付时如实报告：

- **已盘点**：发现的目录、文件、组件、入口、接口、数据源、依赖和场景；
- **已检查**：实际阅读、追踪或运行过的对象，注明深度与方法；
- **未检查**：已知存在但本轮未覆盖的对象及原因；
- **排除项及理由**：依据契约排除的内容，不得只写“无关”；
- **核心链路**：入口到结果、输入到持久化、授权到外部动作等关键路径的覆盖情况；
- **抽样内容**：总体、样本选择方法、数量、代表性和不可外推的边界；
- **无法读取或运行的部分**：权限、环境、依赖、数据或工具限制及其影响；
- **维度适用性**：第四节各类维度中哪些适用、哪些不适用及理由。

“扫描过”“看过主要文件”“抽查无异常”不能替代可复核底账。只检查部分文件、分支或场景时只能声明部分覆盖，不得写“全面检查”或作超出证据的外推。

## 三、独立标准

不得把被审查对象自己的 README、注释、自述、测试名称、规则文本或成功日志作为其正确性的唯一标准。它们提供意图线索，必须与独立标准及真实行为交叉核验。

按对象选择标准：

- 代码与数据流程：用户需求、业务规则、协议、数据约束、调用方契约、真实运行结果；
- 技能、提示词与规范：用户目标、平台能力与限制、目标 Agent 的真实行为、压力场景下的执行结果；
- 文档：实际系统行为、目标读者任务、可操作性、真实命令结果；
- 配置：工具或平台规范、实际运行环境、解析与加载结果、优先级规则；
- 安全与外部操作：授权契约、最小权限原则、数据分类、恢复要求；
- 跨平台事项：目标平台规则和真实设备结果；兼容性推断不能替代实测。

标准冲突时记录冲突、优先级和选择依据。标准本身不明确时，结论保持“疑似待验证”或转为“建议”，不得为获得确定结论而自行发明需求。

## 四、审查维度

以下是选择性线索，不要求机械执行全部项目。契约与底账必须说明各类“适用 / 不适用”及理由；适用项必须追踪完整路径，不能只搜关键词。

- **范围与授权**：目标是否清楚、成功标准是否可验证、非目标是否一致、授权是否覆盖实际动作、结论是否越界。
- **逻辑与数据**：条件、分支、循环、排序、优先级、短路、边界、默认值；类型、单位、精度、舍入、溢出、除零、空值、重复、编码、序列化、聚合一致性。
- **状态与并发**：初始化、转换、重试、取消、恢复、关闭、过期、清理、幂等性；竞态、锁、顺序、超时、重复事件、资源释放、退出行为。
- **错误处理**：错误是否被捕获、保留语义并传达给正确对象；降级、重试、超时是否掩盖失败或造成二次损害。
- **安全边界**：身份、权限、输入校验、注入、路径穿越、秘密、隐私、反序列化、不可信内容是否在正确边界处理。
- **文件与不可逆操作**：读写范围、覆盖、原子性、备份、恢复、权限、数据保留；删除、迁移、支付、发送、发布、远程变更是否具有明确授权、确认和恢复策略。
- **配置与跨平台**：默认值、层级覆盖、环境变量、功能开关、缺失配置、实际加载结果；路径、大小写、编码、行尾、文件名、权限、Shell、区域设置、工具可用性；声明是否有真实证据。
- **文档与实现一致性**：文档、注释、命名、示例和界面承诺是否与实现和运行结果一致，步骤是否足以让目标读者完成任务。
- **依赖与测试**：依赖来源、版本约束、锁定、许可证、维护状态、已知风险；测试是否验证真实行为、断言是否有效、是否覆盖失败与边界、跳过项是否诚实。
- **残留物与未完成实现**：不可达代码、陈旧配置、失效引用、调试输出、占位实现、被忽略的待办、重复实现是否造成实际风险或误导。
- **非代码对象的场景有效性**：规则在正常、模糊、压力、冲突、边界和不应触发场景中是否产生预期行为（见第七节）。
- **修复与证据完整性**：发现、修复、针对性验证、回归验证、DEVLOG 与 AUDIT 关联是否完整；是否把未执行、受限或不确定写成通过。

## 五、失败场景、证据与反证

### 5.1 必须写成可复核的失败链

```text
输入或初始状态 → 执行路径 → 可观察的错误行为 → 实际影响
```

至少回答：什么输入、状态、权限、配置或时序会触发；从哪个入口进入、经过哪些关键分支或加载顺序；实际发生了什么、如何观察；独立标准要求的预期行为；影响谁、影响范围和可恢复性；能否用最小样本稳定复现，不能复现时还缺什么证据。

“可能出错”“看起来不安全”“最佳实践不是这样”“这里没有测试”“理论上会失败”不能单独构成确认问题，只能作为进一步验证的线索。

### 5.2 已确认问题的最低证据

稳定发现 ID；位置（相对路径与行号、配置键、规则段落或其他可重复定位方式）；触发条件；实际行为；预期行为及独立标准来源；完整失败链；证据；影响与边界；反证过程与结果；当前处理；验证状态、方法与关键结果；发生修复时关联的 DEVLOG 稳定 ID；仅在实际存在时填写的 Git commit。

证据应足以让另一位审查者依据相同条件复核。日志与截图只保留与结论相关的最小片段，不泄露秘密或个人数据。工具“未报错”、测试名称、注释声明、作者口头保证或子 Agent 的完成汇报都不能单独证明问题不存在或修复成功。

可接受的证明方式（优先级取决于对象）：隔离环境中用最小输入复现；运行修复前失败、修复后通过的针对性测试；追踪完整调用、状态、数据或规则路径并证明触发条件可达；将真实输出与协议或可信基准逐项对照；对非代码对象使用独立执行者或真实用户场景测试；不能运行时用静态证明记录每个前提，同时把运行验证标为未执行、环境受限或结果不确定。

### 5.3 主动反证

找到支持证据后必须尝试推翻自己的结论。至少检查：上游输入校验、权限控制与规范化；调用方前置条件、类型约束与可达性；框架、运行时、数据库或平台的真实保证；配置默认值、环境覆盖、功能开关与部署前提；其他实现分支、回退路径与重复实现；事务、锁、原子写、重试与补偿机制；业务目标、已接受限制和明确非目标；现有测试是否真正覆盖同一条件而非只有相似名称。

记录检查了什么、依据是什么、为何能或不能推翻结论。合理反证尚未排除、触发路径不可达、独立标准存在争议或关键环境无法验证时，不得标为“已确认”，应降为“疑似待验证”并写明缺失证据与下一步。

### 5.4 误报控制

提交发现前逐项自查：失败场景是否现实可达；是否定位到实际执行路径而非依据命名猜测；是否使用独立标准；反证是否已检查并记录；是否区分“没有证据证明正确”与“已有证据证明错误”；是否考虑环境差异、配置前提、版本条件与非范围；是否复现或明确说明证据缺口；是否避免为同一根因重复报告多个表象；是否把测试缺口与风格偏好保留为建议；严重性是否由现实影响支持而非最坏想象；结论是否限定在已检查范围；是否亲自核验子 Agent、工具或作者提供的结论。

证据不足时降低确定性，不靠增加措辞强度掩盖缺口。连续两轮仍无法验证的疑似项，向用户说明缺失条件，请其选择提供复现条件、接受防御性建议或停止追查；不无限悬挂，也不擅自升格。

## 六、发现分类与验证状态

### 6.1 确定性

- **已确认**：存在具体失败场景，触发路径可达，实际与预期差异有足够证据，合理反证已排除。
- **疑似待验证**：风险有合理依据，但触发条件、独立标准、运行环境或反证仍不完整。必须单列，不得混入确认清单。
- **建议**：不存在已证明的错误行为，是可维护性、清晰度、效率、体验或流程上的改进机会。不得包装成缺陷。

### 6.2 已确认缺陷的严重性

严重性只描述已确认缺陷的影响，**不代表修改授权**：

- **致命**：破坏核心目标、造成不可接受的数据丢失或泄露、不可逆外部后果或系统性安全失陷，且缺少可靠规避与恢复手段。
- **严重**：在现实可达条件下导致关键功能错误、重大数据或安全影响、广泛用户受阻，但范围或恢复条件低于致命级。
- **一般**：非核心功能错误、有限范围偏差或明确边缘场景失败，存在可行规避方式。
- **轻微**：影响有限且易恢复，但仍有可证明的错误行为。

无法证明影响等级时采用证据支持的较低等级并说明不确定性，不靠最坏想象抬级。严重性不得把“疑似”升格为事实，也不得用于绕过只读或有限授权。

### 6.3 建议优先级

改进意见单独使用**高、中、低**优先级，不进入缺陷等级轴。每条写明理由、预期收益、成本、取舍和不实施的影响。优先级是排序依据，不是实施授权。

### 6.4 验证状态五分类

每个检查、复现、测试、构建、运行、修复或回归项必须使用且只能使用以下之一：

- **通过**：方法实际执行，结果满足明确预期，并保存足够关键证据；
- **失败**：方法实际执行，结果不满足预期；记录实际结果与影响；
- **未执行**：尚未运行；说明原因，不推断结果；
- **环境受限**：因平台、权限、依赖、数据、网络或工具限制无法完成；说明限制与可补验条件；
- **结果不确定**：已执行但证据矛盾、不稳定、覆盖不足或无法归因；说明来源与下一步。

静态兼容分析、文档声明、工具返回码为零、局部测试通过或“按设计应可工作”均不得自动记为通过。

## 七、非代码对象的场景测试

技能、提示词、规范、配置和文档不能仅靠逐行通读证明有效。适用时必须构造以下六类场景，记录输入、环境、观察到的行为、预期行为、证据和状态：

1. **正常场景**：信息充分、无冲突，验证主流程能完成；
2. **模糊场景**：目标、范围、术语或授权含糊，验证会澄清而不是猜测；
3. **压力场景**：时间紧、用户催促、已有投入或高严重性发现下，验证关键纪律仍被遵守；
4. **冲突场景**：用户要求、项目规则、平台限制或多个指令互相冲突，验证能识别优先级并停止越权；
5. **边界场景**：空输入、极端长度、首尾值、重复执行、权限不足、路径相邻或平台差异；
6. **不应触发场景**：相似关键词但意图不属于该流程（纯解释、孤立拼写修正、普通问答），验证不会过度触发。

应尽量使用与目标平台一致的新上下文或独立执行者，避免测试者凭已知答案补全规则缺口。无法进行真实场景测试时，静态阅读结果不能写成有效性通过，应记录未执行、环境受限或结果不确定。

## 八、审查与修复严格分离

```text
发现候选 → 验证失败场景 → 主动反证 → 记录审查结论 → 检查修改授权
→ 建立 DEVLOG 工作单元 → 实施修复 → 针对性验证 → 回归验证
→ 向原 AUDIT 发现追加处理结果
```

1. 修复不是审查的默认组成部分。只读授权下停在“记录审查结论”，任何级别都不得修改。
2. 有修改授权也必须核对确切范围；授权只覆盖点名对象时，不得顺手重构相邻模块。
3. 修复前在 `DEVLOG.md` 建立带稳定 ID 的工作单元（如 `D-014`），记录来源 AUDIT ID、目标、方案、影响范围和预期验证。
4. 修复后在同一工作单元追加实际变更、针对性验证、回归验证、偏差、遗留项和五分类状态。
5. 在 `AUDIT.md` 对原发现**追加**处理结果并关联 DEVLOG ID；不得覆盖原始失败场景、证据或反证记录。
6. 只有用户可见修复已经落地时才考虑更新 CHANGELOG；仅有审查结论不进入 CHANGELOG。
7. 修复失败、验证失败、未执行、环境受限或结果不确定时，如实保留对应状态，不得把“已修改”写成“已修复”。
8. 修复需要删除、覆盖、批量重命名、不可逆迁移、外部发布或超出既有授权的动作时，必须另行取得具体授权。

## 九、复审

复审不是重新出具一份孤立报告。开始时先读取上一轮覆盖底账和全部未闭环项，然后：

1. 核对对象版本、环境、契约和授权是否变化；
2. 逐项复查上轮待处理的已确认问题、疑似项和已采纳建议；
3. 对声称已修复的项目读取实际变更，核对关联 DEVLOG ID；
4. 重跑原失败场景，确认错误不再发生；
5. 运行受影响核心链路和适用回归测试；
6. 检查修复是否引入新的数据、状态、安全、兼容性或文档不一致；
7. 对无法复验项使用五分类状态并写明原因；
8. 更新覆盖底账，明确新增、重复和仍未覆盖内容；
9. 在 AUDIT 中追加复审结果，不覆盖旧轮次或原发现。

只有原失败场景不再出现、针对性验证通过、适用回归验证有真实结果且没有未解释的关键副作用时，才能记录为“已修复”。用户决定接受风险时记录“已接受”及依据，不得改写为“无问题”。
