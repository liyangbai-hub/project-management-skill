# 项目事实层与记录模板

本文件提供可直接采用的项目事实层模板。使用时应先根据项目事实删改占位内容和无意义的空章节，不要机械复制。项目保持原生工具链和源码布局；不要求创建 `技术/`，也不要求移动或重排源码。

## 一、最小目录原则

推荐的事实层如下：

```text
<project-root>/
├── AGENTS.md
├── CLAUDE.md
├── README.md
├── DEVLOG.md
├── CHANGELOG.md
├── requirements/       # 仅在确有输入材料时创建
│   └── INDEX.md
└── AUDIT.md             # 受管项目首次执行模式三时创建
```

采用规则：

- `AGENTS.md`、`CLAUDE.md`、`README.md`、`DEVLOG.md`、`CHANGELOG.md` 是推荐事实层；内容必须来自实际项目，不应只留下空模板。
- `requirements/` 仅在项目确有需求文档、调研资料、用户附件或其他输入材料时创建；没有材料时不创建空目录或空索引。
- `AUDIT.md` 仅在受管项目首次执行证据化审查时创建；普通开发不预建空文件。
- 已有项目使用 `需求/` 时继续识别，不强制迁移或改名。
- 源码、测试、资产、配置和文档目录服从原生工具链，不强制放入 `技术/` 或任何统一源码目录。
- 文档提供当前地图和接力入口，不替代代码、配置、依赖清单和实际验证。
- Git 推荐但可选。没有 Git 不阻塞使用；不自动执行 `git init` 或 commit。创建远程仓库、push、远程分支、PR、Release 等操作必须取得用户明确授权。

## 二、`AGENTS.md` 模板

`AGENTS.md` 是工具中立的项目工作协议正本。应按项目实际情况补充具体命令和边界，使其无需依赖某个 Agent 的聊天记录即可使用。

```markdown
# 项目工作协议

## 开工顺序

1. 阅读本文件并遵守现行协议。
2. 阅读 `README.md`，了解项目目的、当前能力、关键文件、运行方式和已知限制。
3. 阅读 `DEVLOG.md` 顶部的“当前状态”，再阅读文件末尾与本轮工作相关的工作单元和补充记录。
4. 若存在 `requirements/INDEX.md`，检查“待评估”或“部分采纳”的材料；同时兼容识别已有 `需求/` 目录和带 `[已读]` 前缀的历史材料。
5. 查看实际代码、配置、依赖清单和适用命令，核验本轮依赖的关键事实；不要把文档声明自动视为已验证事实。

## 改动与留痕

- 以有意义的工作单元为粒度管理改动，不为每次工具调用或每行修改单独建记录。
- 在实质实施前，在 `DEVLOG.md` 追加工作单元计划，写明目标、背景、计划、影响范围和预期验证。
- 实施后运行适用验证，在同一工作单元后追加结果，写明实际完成、变更文件、验证、偏差、遗留项和状态。
- 更新 `DEVLOG.md` 顶部“当前状态”，为下一位接手者留下当前阶段、最近完成、正在进行、下一步、阻塞项和关键验证命令。
- 只有已经落地的用户可见新增、变更、修复或移除才写入 `CHANGELOG.md`；计划、调查过程、内部整理和未完成工作不写入。

## 历史规则

- `DEVLOG.md` 历史条目正文只追加，不覆盖、不删除，不回头改写旧计划来补状态。
- 状态变化通过新的“结果”或“补充”小节追加；顶部“当前状态”是通常唯一可正常改写的区域。
- 不改变语义的拼写修正可以直接完成。
- 若敏感信息误入记录，允许就地脱敏，但必须追加脱敏说明；已经暴露的凭据还需轮换，并根据实际风险处理其他副本或 Git 历史。
- 审查历史写入 `AUDIT.md`；修复时用稳定 ID 关联对应 DEVLOG 工作单元。

## 材料规则

- 原始材料默认不重命名、不修改、不删除。
- 新材料的处理状态、吸收位置和结论记录在 `requirements/INDEX.md`。
- 新流程不通过添加 `[已读]` 前缀表示处理完成；已有 `[已读]` 文件只作为历史兼容信号，仍需结合索引和实际内容判断状态。

## 安全与授权

- 不在代码、日志或公开文档中写入凭据、令牌、私钥、真实 `.env` 值或个人隐私数据。
- 删除、覆盖、批量重命名、不可逆迁移等操作必须先取得针对具体范围的明确授权。
- 只读任务不得修改文件、配置、历史或元数据。
- 未经明确授权，不创建远程仓库，不 push，不修改远程分支，不创建 PR 或 Release，也不执行其他外部发布操作。
- 本地 Git 是可选工具；不得自动初始化仓库或自动 commit。一个 DEVLOG 工作单元可对应零个、一个或多个 commit。

## 验证与交付

- 验证结果明确标记为：通过、失败、未执行、环境受限或结果不确定。
- 不把兼容性设计、静态推断或文档声明描述成真实运行通过。
- 完成时报告实际范围、改动内容、验证依据、未覆盖项、遗留问题和授权边界遵守情况。
```

## 三、`CLAUDE.md` 模板

`CLAUDE.md` 保持简短，只作为入口桩，不复制一套可能漂移的项目协议。可直接采用以下纯文本：

```text
本项目的完整工作协议位于同目录的 AGENTS.md。任何改动前必须先阅读并遵守 AGENTS.md。
```

## 五、`DEVLOG.md` 模板

### 使用规则

- 顶部“当前状态”是通常唯一可正常改写的区域。
- 历史以有意义的工作单元追加。计划和结果共用稳定 ID，例如 `D-001`；后续依次使用 `D-002`、`D-003`，已使用的 ID 不回收、不改号。
- 标题时间必须是记录发生时的真实本地日期和时间，推荐格式为 `YYYY-MM-DD HH:mm`。模板中的 `<真实时间>` 必须替换，不得保留占位符，也不得编造执行时间。
- 实质实施前追加计划；结束或发生重要状态变化后追加结果或补充。不要回头把旧计划中的“进行中”改成“已完成”。
- 验证逐项记录命令或方法、状态和关键结果。未运行就写“未执行”，环境不具备就写“环境受限”，证据不足就写“结果不确定”。
- 工作单元不等于 commit：一个工作单元可对应零个、一个或多个 Git commit；不默认自动 commit。

```markdown

  1.

- 影响范围：
- 预期验证：
```

### 状态通过追加更新的示例

下例演示“旧计划不回写，状态通过追加结果和补充更新”。示例时间仅说明格式，实际项目必须写真实时间。

```markdown
## D-001｜2026-07-27 14:30｜计划：完善导入流程

- 目标：让用户能够导入 UTF-8 CSV 并看到明确的校验错误。
- 计划：确认现有字段约束和入口；实现解析与校验；增加正常和错误输入验证。
- 影响范围：导入入口、字段校验、相关测试和 README 使用说明。
- 预期验证：运行项目原生测试命令，并手工验证一个有效文件和两个无效文件。
- 状态：进行中

### D-001 结果｜2026-07-27 16:10

- 实际完成：增加 CSV 解析、必填字段校验和错误行号提示。
- 变更文件：
  - `src/importer.ts`：实现解析与校验。
  - `tests/importer.test.ts`：覆盖有效输入和缺失字段。
- 验证：
  - `npm test -- importer`：通过；12 项测试全部通过。
  - 手工验证非法编码文件：未执行；当前没有该类样本。
- 偏差与原因：非法编码场景未验证，因本工作单元未取得测试样本。
- 状态：部分完成

### D-001 补充｜2026-07-28 09:20

- 内容：补充非法编码 fixture 并完成回归验证。
- 验证：`npm test -- importer`：通过；新增场景通过。
- 状态：已完成
```

### 历史追加和例外

- 已追加的计划、结果和补充正文不得覆盖、删除或为“看起来整洁”而重写。
- 顶部“当前状态”可以随实际状态更新；README 也可以按当前事实维护。
- 纯拼写、标点或格式修正且不改变语义时，可以直接修正历史文本。
- 敏感信息误入时，应先停止扩散并就地脱敏，再追加说明脱敏位置、原因和处置；凭据已经暴露时还必须轮换，Git 存在时根据风险评估历史清理。

建议的脱敏说明格式：

```markdown
### D-<ID> 记录修正｜<真实时间>

- 修正：已将此前误写入的敏感值替换为 `<已脱敏>`。
- 原因：防止继续扩散；本次修正不改变工作结论。
- 后续处置：<凭据轮换、其他副本检查、Git 历史处理或不适用说明>。
```

## 六、`CHANGELOG.md` 模板

`CHANGELOG.md` 只记录已经落地的用户可见变化。计划、调查过程、内部重构但无用户可见影响、审查结论和未完成工作不进入 CHANGELOG。发布项目可按版本归档；无版本项目可按日期追加。

```markdown
# Changelog

## Unreleased

### Added

- <已经落地的用户可见新增>

### Changed

- <已经落地的用户可见变化>

### Fixed

- <已经落地的用户可见修复>

### Removed

- <已经落地的用户可见移除>
```

发布项目归档示例：

```markdown
## [0.2.0] - 2026-07-27

### Added

- 支持导入 UTF-8 CSV 文件。
```

无版本项目示例：

```markdown
## 2026-07-27

### Fixed

- 修复月末报表遗漏最后一天数据的问题。
```

没有对应变化的分类应删除，不保留机械空标题。

## 七、`AUDIT.md` 模板

`AUDIT.md` 在受管项目首次执行模式三时创建，之后按审查轮次和发现追加历史。确定性与严重性分开：

- 已确认问题：已经有具体失败场景和足够证据，可使用“致命、严重、一般、轻微”严重性。
- 疑似待验证：存在合理风险但证据不足，不能混入已确认问题，也不提前赋予已确认结论。
- 建议：改进机会，不包装成缺陷，使用“高、中、低”建议优先级。

修复不是发现的默认后续动作。先记录结论，再检查授权；获准修复时建立 DEVLOG 工作单元，修复与回归后向原发现追加处理结果，不覆盖原始证据。

文件以 `# 审查记录` 开头，其后按轮次追加。**完整的轮次、发现和处理补充结构只在 [`audit-checklist.md`](audit-checklist.md) 第十节维护一份，不在本文件重复。**

已确认问题的实际填写示例：

```markdown
## A-20260727-001｜严重｜已修复

- 位置：`src/importer.ts:42`
- 触发条件：导入包含空必填字段的 CSV。
- 实际行为：记录被静默写入，后续汇总报错。
- 预期行为：导入阶段拒绝该行并报告行号。
- 证据：使用最小输入复现；测试在修复前失败。
- 影响：可能产生不完整数据并延迟暴露错误。
- 反证检查：调用方未做等价校验，配置中也没有必填保证。
- 处理：在写入前增加必填校验。
- 验证：通过；针对性测试和现有回归测试均通过。
- 关联 DEVLOG：D-014
- 关联 Git：无
```

## 八、`requirements/INDEX.md` 模板

材料索引是当前可维护的评估台账。原始材料默认不重命名、不修改、不删除；使用相对路径记录，避免复制作者机器绝对路径。

允许状态只有：

- 待评估：尚未完成内容判断。
- 已评估：已判断并记录结论，不代表全部采纳。
- 部分采纳：仅部分内容进入项目，必须说明采纳与未采纳部分。
- 暂缓：当前不处理，必须说明原因或重评条件。
- 拒绝：明确不采用，必须记录理由。

可直接采用：

```markdown
# 输入材料索引

## 使用规则

- 原始材料不因评估而重命名、修改或删除。
- 新流程不添加 `[已读]` 前缀；状态只记录在本索引。
- 已有 `需求/` 和 `[已读]` 文件作为历史兼容信号继续识别，但 `[已读]` 不自动证明内容已完整吸收；必要时重新核对材料、现有实现和历史记录。
- “已吸收至”填写 README 章节、DEVLOG ID、代码或其他相对路径；没有吸收时写 `—`。

## 材料

| 文件 | 状态 | 已吸收至 | 结论 |
|---|---|---|---|
| `战斗系统构想.md` | 部分采纳 | `README.md`、`DEVLOG.md` 的 `D-008` | 采纳连击机制；PvP 暂缓，等待同步方案 |
| `competitor-notes.pdf` | 已评估 | `README.md` | 仅作背景参考，不直接复制功能 |
| `新需求.md` | 待评估 | — | — |
| `需求/[已读]历史方案.md` | 已评估 | `DEVLOG.md` 的 `D-003` | 历史兼容文件；已重新核对实际吸收范围 |
```

更新索引时：

1. 先阅读材料并核对其与当前项目事实的关系。
2. 更新状态、吸收位置和结论；部分采纳、暂缓和拒绝必须给出边界或理由。
3. 若评估形成实施工作，在 `DEVLOG.md` 建立工作单元并从索引关联稳定 ID。
4. 不通过改文件名表示完成，不因索引更新而删除原始输入。

## 九、模板间的一致关系

| 事实或动作 | 正式记录位置 |
|---|---|
| 当前项目目的、能力、架构、运行方法、限制和路线 | `README.md` |
| 当前阶段、接力起点、计划、决策、实施结果和偏差 | `DEVLOG.md` |
| 已落地的用户可见变化 | `CHANGELOG.md` |
| 材料状态、吸收位置和结论 | `requirements/INDEX.md` |
| 审查契约、覆盖底账、证据化发现和处理历史 | `AUDIT.md` |
| Agent 的开工、留痕、安全和授权协议 | `AGENTS.md` |
| Claude Code 的协议入口 | `CLAUDE.md`，仅指向 `AGENTS.md` |

同一事实需要交叉引用时，使用稳定 ID 或相对路径建立联系，不复制多套相互竞争的状态。例如：`AUDIT.md` 的确认问题关联 `D-014`，`DEVLOG.md` 的结果记录修复和验证，只有修复已经落地且用户可见时才在 `CHANGELOG.md` 增加对应条目。
